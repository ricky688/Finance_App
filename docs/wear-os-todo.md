## 銀行轉帳收款／收入確認：手機與手錶協作

目標：使用者收到銀行 App 的入帳通知後，可以在手錶決定這筆通知是否記入 VibeFinance，以及適用的收入／轉帳分類。此功能確認的是記帳決定，不執行銀行轉帳，也不把通知辨識當成銀行結算驗證。

### 使用流程

- [ ] 手機在使用者已授權的通知存取與銀行 App 篩選範圍內偵測收款；先驗證各銀行實際通知是否能提供足夠資訊。
- [ ] 重用手機 `PaymentNotificationListener`、`PendingPaymentStore` 與既有轉帳決策流程；只有尚待人工決定的項目送到手錶，已由手機完成的項目不可再次要求記帳。
- [ ] 手錶顯示完整單行金額、來源銀行、時間、辨識出的類型與遮罩後的帳戶提示；提供「確認收入」、「自有帳戶轉帳」（資訊足夠時）、「忽略」、「稍後處理」及「在手機處理」。
- [ ] 區分外部收款／薪金等收入與自有帳戶間轉帳，維持手機既有收支、轉帳及預算排除規則。方向、來源／目的帳戶或分類不明時轉交手機，不由手錶猜測。
- [ ] 首版只支援手機已能明確辨識、且可映射至有效帳戶的決策；需要新增帳戶、補齊轉帳對端或複雜編輯時在手機繼續同一筆項目。
- [ ] 手錶送出選擇後顯示「等待手機確認」；收到手機持久化成功回覆才顯示「已記帳」。失敗時保留待處理項目並提供重試，不假裝成功。
- [ ] 任一端完成、忽略或撤銷項目後，另一端同步結果並移除過期操作；「稍後處理」保留手機待辦。

### 共用狀態與資料完整性

- [ ] 手機作為唯一記帳來源；手錶不直接修改帳戶餘額、不複製銀行通知解析或金融算法。
- [ ] 以手機既有待確認項目 ID／去重識別連結兩端，另外定義具版本的操作、請求 ID、項目 revision／有效期限與明確成功／失敗回覆；不把目前唯讀預算快照當成交易寫入協定。
- [ ] 手機重新驗證項目仍待確認、帳戶有效、決策允許且未過期，再委派既有正式記帳流程。重複點按、訊息重送、手機與手錶同時確認都只能產生一筆有效交易。
- [ ] 手機已處理或資料被替換的舊項目，在手錶顯示「已在手機處理／項目已失效」，不得重新建立交易。
- [ ] 處理手機／手錶程序重啟、送出後斷線、成功回覆遺失與重連；首版離線時只保留待辦，不把未確認的選擇自動補送成已記帳交易。
- [ ] 使用者若需要修改決策或撤銷已記帳項目，沿用手機既有能力與原交易識別，不以建立第二筆交易代替撤銷。

### 授權與隱私

- [ ] 新增獨立的「在手錶處理待確認交易」選項，預設關閉；既有「分享預算」不自動授權分享交易或寫入記帳決策。
- [ ] 限定已配對且授權的手機／手錶；驗證傳送來源、操作內容、期限與重放，不接受任意節點傳來的記帳命令。
- [ ] 定義並驗證 App lock、隱藏金額、手錶鎖定、關閉分享與解除配對時的顯示及操作限制；手錶確認不得繞過手機既有解鎖要求。
- [ ] 僅傳必要摘要與受限的帳戶識別／遮罩提示；不傳整段銀行通知、完整帳號、驗證碼或銀行登入資料，診斷記錄不含敏感內容。

### 驗收案例

- [ ] 已辨識的外部收款／薪金，在手錶確認後手機只新增一次正確收入記錄。
- [ ] 自有帳戶轉帳、轉出通知、退款、八達通增值及模糊通知不被誤當新增收入；沿用並測試手機既有分類結果。
- [ ] 手機與手錶同時確認、連點、重送及成功回覆遺失，都不重複記帳；驗證帳戶餘額、轉帳兩端及預算結果。
- [ ] 忽略、稍後處理、手機先完成、帳戶刪除、舊 revision、過期及重新啟動，兩端狀態一致。
- [ ] 覆蓋離線／重連、隱私撤回、App lock 與手錶鎖定，不能在失敗或等待時顯示已入帳。
- [ ] 測試使用正式手機處理函式與真實手錶 Composable，搭配記憶體／隔離 fixtures；互動測試編寫前先用 ARTEMIS 探索。API 36／37、圓形螢幕與 app-scoped 大字體均需驗證，不修改真實帳目或裝置縮放設定。
